# ADR 2026-10-12: Git stack for vault sync

**Status**: Accepted (validated by the sync spike, 9/9 tests incl. SIGKILL convergence)
**Context**: cross-platform Markdown vault — macOS, Linux, iOS/iPadOS, Android

## Context

The riskiest assumption was that a shared Rust core could perform reliable Git sync and
conflict recovery on all five platforms. Two candidate Git stacks: `gitoxide` (pure Rust,
easy mobile cross-compilation) and `libgit2` (complete, but C — needs vendored build for
mobile). A spike was built: `crates/vault-core` (engine), `crates/vault-spike-cli`
(harness), bare-repo remote, full test suite: happy path, concurrent non-overlapping and
overlapping edits, delete-vs-edit, offline-then-online, nested dirs, and process-kill at
every sync state transition.

## Decision

1. **Hybrid Git transport, hidden behind one `GitBackend` trait**
   - `gix` 0.89: repo init/open, object/blob/tree writes, commits, fetch, merge-base, ancestry
   - `git2` (libgit2): **push** — gitoxide has no receive-pack implementation at all, and
     mobile targets cannot shell out to a git binary
   - Mobile builds vendor libgit2 (`git2/vendored`); requires cmake in the toolchain

2. **Merge policy** (validated in spike)
   - Non-overlapping concurrent edits: line-level three-way merge via `imara-diff`
     (`Diff::compute` + `hunks()`), auto-commit
   - Overlapping edits: last-writer-wins by `(committer_time, oid)` — deterministic and
     symmetric so both clients converge; loser preserved as `note.conflict-<ts>.md` and
     synced; conflict rows recorded in SQLite
   - Delete vs. edit: edit wins, deleted version preserved as conflict copy

3. **Sync model**: single `main` branch, linear history, no rebase of published commits;
   sync exposed to hosts as one idempotent `sync(vault)` call; every transition journaled
   to SQLite; scheduling lives in the app shell, never in the core.

## Evidence: gitoxide evaluation log

| Area          | Finding                                                                                                     | Impact / workaround                                   |
| ------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| push          | `gix` 0.89 has **no push support** (no receive-pack anywhere, incl. `gix-protocol`)                          | Hard gap → libgit2 for push (this decision)             |
| config        | `config_snapshot_mut()` is in-memory only, never persists to `.git/config`                                   | `config_file_mut()` transaction + repo reopen           |
| commits/trees | No high-level "stage + commit" over a worktree; trees/commits written manually                                | ~120 lines custom plumbing (git tree sort order) — fine |
| merge         | No tree/file merge in `gix`; built on `imara-diff`                                                           | ~200 lines; imara-diff API clean and sufficient         |
| identity      | Isolated config has no committer; ref updates fail ("reflog messages need a committer")                      | `committer_or_set_generic_fallback()` on open           |
| fetch         | `find_remote` + bisync `connect`/`prepare_fetch`/`receive` works on local remotes (blocking feature)          | None — clean                                            |

Decision rule was: **> 2 weeks of plumbing or any correctness gap in merge/push → libgit2.**
Result: merge/recovery passed with modest plumbing; push was a hard capability gap → hybrid.

## Consequences

- The engine (`vault-core`) is transport-agnostic; the libgit2 dependency is confined to
  `gix_backend.rs::push_main` and can be swapped without touching sync/merge logic
- Re-evaluate pure-gitoxide if push support lands upstream
- Retry with capped exponential backoff (network-class errors only) is **not yet
  implemented** — deferred to mobile milestone where flaky networks first appear
- Spike harness (`vault-spike-cli`) and its crash-injection hook stay as the conformance
  suite for future platforms (mobile validation runs the same tests)
