# ADR 2026-10-29: Sync flow runs in-process — no git subprocess anywhere

**Status**: Accepted (validated by code audit during Phase 1, FND-12/13 refactor)
**Context**: concern raised during review — "it seems we are just calling git via the terminal"

## Question

Is the app's Git synchronization real, or does the desktop app shell out to a `git`
executable through the terminal?

## Evidence (audit results)

1. **No git subprocess exists.** A full-text audit of `crates/vault-core/src` and
   `md-app/src-tauri/src` finds no `std::process::Command` invoking `git` — the only
   process-level calls are `std::process::abort()` (the crash-injection hook in
   `sync.rs`, test-only via `VAULT_SPIKE_ABORT_STATE`) and `std::process::exit` in the
   `vault-cli` test-harness binary.
2. **The engine talks to libraries, not executables.** `vault.rs` wires
   `pub git: GixBackend` — an in-process implementation of the `GitBackend` trait using
   `gix` 0.89 (init/open, fetch, merge-base, trees/commits) plus `git2`/libgit2 for
   push (see ADR 2026-10-12 for why the transport is hybrid).
3. **The sync state machine is ours, in-process.** `sync.rs::sync_inner` runs:
   commit pending → fetch → merge-base → three-way merge (imara-diff) with
   last-writer-wins + conflict copies → create commit → update `main` → push. Every
   transition is journaled to SQLite (`begin_run` / `event` / `finish_run`), which is
   what the UI's git panel renders.
4. **App wiring confirms the path.** UI (`git-panel.tsx`, `useVault`) → Tauri commands
   `vault_sync` / `git_action` / `git_state_cmd` (`commands/git.rs`, `commands/vault.rs`)
   → `sync::sync_with` / `push_now` / `take_remote` / `force_publish`. No terminal, no
   shelling, no git CLI dependency at runtime.
5. **No terminal prompts are possible.** `lib.rs::run` sets `GIT_TERMINAL_PROMPT=0` and
   `GIT_ASKPASS`/`SSH_ASKPASS` to `/bin/true`, so auth failures surface as typed errors
   (`code: "auth"`) handled by the credentials dialog — another sign the flow never
   expected an interactive terminal.

## Why the confusion may have arisen

- The sync journal surfaces human-readable step names ("Fetching", "Merging", "Pushing")
  that resemble git CLI output.
- `vault-cli` (a developer test harness binary inside vault-core) is invoked from
  terminals during development; it is not part of the app runtime.
- Credentials are entered via the UI dialog and passed per-call (`CredentialsDto`) —
  which can look like a remote-exec path but is only an argument over IPC.

## Consequences

- Confirmed: mobile targets (no git binary, no shell) are compatible with the current
  design; the GitBackend trait hides any future transport changes.
- Remaining honest gaps, tracked for later phases: credentials are held in memory per
  call and never persisted (fine for the current trust model, revisit under MOB-04);
  sync scheduling is user-triggered only — background sync stays out until conflict
  handling is proven (Phase 4 rule).
- The audit checklist above should re-run whenever a new transport backend is added.
